# Independent Validation Programme v1.0 — executable research protocol

**Status:** proposed independent testing protocol, **not** a new governance framework or amendment to frozen sources.  
**Programme:** Enterprise AI Agent Fabric / Decision-to-Evidence Engineering  
**Date:** 2026-11-24  
**Scope:** D-10, D-14, D-18, Chapter 13, Chapter 16, Meridian Fixture v1.0, knowledge usability, author/human/AI handover, operating-system enforceability and publisher comprehension.  
**Excluded:** redesign of four layers, eight planes, 58 chapters, 30 Atlas IDs/defaults, Meridian chronology/identity/evidence; claims of certified assurance; real financial action tests.  
**Authority:** existing `REPOSITORY-GOVERNANCE.md`, frozen F1/F6/F7, programme OS and baseline; this protocol tests them without replacing their approval authorities.  
**Explicitly NOT YET RUN:** all participant, independent practitioner, publisher and deployed-control trials. Any example expected response here is an **assessor key**, not a measured outcome.

## Part 1 — What is being tested and what evidence counts

We test seven questions, not abstract satisfaction: (1) Can an unaided newcomer navigate a clean checkout? (2) Can two architects independently apply D-10/D-14/D-18 to identical evidence and agree on *what is permitted and why*? (3) Can a junior engineer distinguish retrieved evidence, unresolved truth, and durable memory? (4) Can a security reviewer reconstruct enforcement and disprove a claim of non-bypassability? (5) Can a different AI or human continue a work item from a handover packet without chat history? (6) Can actual branch/CI/review controls stop a prohibited promotion? (7) Can a technical reviewer and publisher understand the proposed book sample without the author briefing them?

### Four evidence levels — never collapse them

| Level | Operational meaning | Acceptable proof | Prohibited inference |
|---|---|---|---|
| SPECIFIED | Document states an expected mechanism | Approved source path, SHA, explicit claim | That the mechanism exists at runtime |
| IMPLEMENTED | Executable rule/configuration/code exists in a pinned build | Repository commit, executable artefact, threat/rights context | That it was reproduced by others |
| REPRODUCED | A reviewer executes exact instructions and observes expected positive and negative outputs | Logs, screenshots where necessary, command transcript, hash, inputs/results | That separate reviewers agree or production safety is proven |
| INDEPENDENTLY_VALIDATED | Qualified non-author repeats test from clean environment, grades a blind case, or tries to falsify controls | Reviewer identity, independence disclosure, evidence hash, scorecard, exception decisions | Universal, regulatory or vendor certification |

**Gating rule:** Never label a feature `REPRODUCED` solely for passing a document linter. Never label it `INDEPENDENTLY_VALIDATED` if the original designer served as the only reviewer. Preserve unsuccessful and aborted runs; an invalid run is neither a pass nor a silent exclusion. Grade only the aspect actually tested (e.g., fixture consistency versus deployed Gateway security).

## Part 2 — Who tests what

| Participant | Minimum profile / independence | Tests | What success means |
|---|---|---|---|
| Junior engineer (J) | Not previously taught the Meridian answer key | IV-01, IV-05, IV-06, IV-08 | Locates sources, identifies conflict and denial without confusing decisions/receipts |
| Senior engineer (S) | Can inspect code/config; not author of test harness | IV-01, IV-04, IV-08, IV-09 | Reproduces outputs and identifies false exactly-once / network claims |
| Enterprise architect A | Independent of fixture author and architect B | IV-02, IV-03, IV-07 | Writes bounded action decision with justified source evidence |
| Enterprise architect B | Independently recruited; no shared prework with A | IV-02, IV-03, IV-07 | Same actionable verdict and major reasons under blind identical inputs |
| Principal engineer | Independent technical challenger, not designer | IV-04, IV-09, IV-10 | Falsifies broken controls or returns evidence-backed limit/NO GO |
| Security reviewer | Qualified in authorisation, federation and tool security | IV-03, IV-04, IV-10 | Differentiates PDP/PEP/egress; rejects simulated signature as real |
| Publisher/development editor | Has not worked on the proposal | IV-11 | Can articulate audience, teaching value, market position, evidence limits |
| External practitioner | No prior session context or author assistance | IV-01, IV-07 or IV-08 | Applies decision/pattern in realistic bounded task and supplies traceable result |
| Coordinator | Project architect; administers packets but must not score own work | All | Preserves assignment randomisation, time, failures and chain of custody |

**Minimal feasible cohort:** 2 independent architects, 1 junior, 1 senior/principal engineer, 1 security reviewer, 1 publisher/editor; roles may overlap only if that does not compromise independence on the same claim. Use different reviewers for the author and security-critical claims. Target a 6–8 participant set if accessible; do not pretend the solo architect can simulate an independent cohort. Obtain consent to record timing/errors, minimise personal data, anonymise published scores, never publish identities without consent.

**Blindness:** distribute the participant brief without the assessor key, this master coordinator protocol, previous chat, research verdict or scoring sheet of expected outcomes. Each participant declares prior familiarity; cases are assigned individually and timeboxed. The coordinator discloses the fixture is synthetic but not its decision outcomes. Examiner records all coaching; any substantive prompt changes validity to `ASSISTED`.

## Part 3 — Scenario scripts with frozen answers

Every scenario is **synthetic** and does not involve a real customer, bank, service account, payment processor, network firewall or production environment. Full exact field values must be read from the supplied immutable JSON in the approved checkout, not replaced with invented examples.

### IV-02 — D-14 / Chapter 13: unresolved status

**Participant brief (20 min):** Investigate whether customer product eligibility can be concluded from `MF-REC-A-001` and `MF-REC-B-001` using `MF-EVD-CM-001`, `MF-EVD-RC-001` and `MF-EVT-005`–`MF-EVT-008`. Report which inputs may be admitted, whether product status is established, who should decide, and whether a durable memory fact can be written. Also inspect `MF-EVT-002`–`004` for the mislabelled insurance item. Include record IDs and source-level access decision.

**Scoring:** The private assessor key defines the expected values and source-level controls. Record evidence IDs, a 0–10 score and any safety hard stop; the key is distributed only through the restricted examiner packet.

### IV-03 — D-10 / Chapter 16: action admission

**Participant brief (20 min):** From `MF-REQ-REF-001`, `MF-EVD-DG-001`, `MF-EVD-AU-001`, `MF-EVD-DN-001` and `MF-EVT-009`–`012`, decide whether `MF-ACT-REF-001` may invoke `refund.issue` (`POST /refunds`) for £125. Report effective versus required scope, approvals, context preconditions, action outcome, and what the receipt actually proves. Distinguish issuer, PDP, PEP and external tool.

**Scoring:** The private assessor key defines the expected values and source-level controls. Record evidence IDs, a 0–10 score and any safety hard stop; the key is distributed only through the restricted examiner packet.

### IV-04 — D-18 / Chapter 16: bypass and proof limits

**Participant brief (20 min):** Auditor claims “Since the Gateway denied, the network is proven non-bypassable.” Test the claim using `MF-EVT-013` and `MF-EVD-DN-001`. Identify exactly two distinct denials and propose **non-destructive** control evidence required before a production non-bypassability assertion could be accepted.

**Scoring:** The private assessor key defines the expected values and source-level controls. Record evidence IDs, a 0–10 score and any safety hard stop; the key is distributed only through the restricted examiner packet.

### IV-05 — Chapter 13 teaching test

**Participant brief (25 min):** After reading Chapter 13 alone, create a one-page table separating retrieval, source-level access, Context Manifest, reconciliation, semantic identity, escalation and durable memory. Explain the two-week sequence and where uncertainty must persist. Supply a case counterexample. **Do not score until a frozen chapter text exists**; the existing F6 blueprint cannot substitute for prose.

**Scoring:** The private assessor key defines the expected values and source-level controls. Record evidence IDs, a 0–10 score and any safety hard stop; the key is distributed only through the restricted examiner packet.

### IV-06 — Chapter 16 teaching test

**Participant brief (25 min):** After Chapter 16 alone, draw an actor-chain/PEP/target sequence and identify the first point of forbidden external side effect, the purpose of D-10 versus D-18, and what later release-gate failure means, using `MF-EVD-RG-001` as source evidence. Do not show Figure 16 answer key during the teach-back.

**Scoring:** The private assessor key defines the expected values and source-level controls. Record evidence IDs, a 0–10 score and any safety hard stop; the key is distributed only through the restricted examiner packet.

### IV-07 — paired blind architect decision trial

Both architects get identical pinned input files and a standard answer form (no key), working independently. Each supplies `(verdict, primary reason, secondary reasons, evidence IDs, exceptions, proof strength, unresolved questions)`. Compare by rubric; disagreements are recorded **before** discussion; never revise original answers after consensus. Require at least one case with no authorised business answer (D-14) and one adverse control result (D-10). A matched wrong answer counts as **agreement but failure**, not success.

### IV-08 — knowledge article/pattern use test

Provide one goal (e.g. “decide whether to allow the refund tool call”) rather than filenames. Participant locates the most relevant **approved** article/pattern and Atlas page, identifies canonical source, executes the example or negative test, cites the source and lists limitation. Grade findability, understanding, correctness, reuse, and no human prompting. No placeholders qualify; 3 articles and 2 patterns with approved releases are prerequisite. Include one **deliberately stale** article to test freshness warnings without misleading the participant about its status.

### IV-09 — blind AI/human handover test

Create a disposable task on a pinned branch and stop after one documented change. Different contributor (GPT→Claude Code, Claude Code→Copilot, or human), with no past chat, gets only repository URL, approved operating contract, handover packet and permitted tools. They must reconstruct canonical source/HEAD, task state, last action, test results and next safe command; make one safe, non-frozen change; request review without rewriting original facts. Grade 10 points: exact SHA 2, task/scope 2, tests/limits 2, safe action 2, source/authority 2. Model output is a suggestion until human-validated. Record model/version, tool permissions, input hash, access level, prompt and output.

### IV-10 — enforced negative workflow test

In a disposable branch (not on `main`) submit three PR simulations: (a) intentionally change one canonical Meridian fixture value; (b) change a frozen decision default; (c) create a security-relevant technical claim lacking independent approval. The intended gate must reject each before merge. Separately submit one allowed, properly reviewed research note and demonstrate it can merge. Verify actual GitHub ruleset/check names and log links: a JSON schema check by itself does **not** prove that GitHub blocks merges. Restore/close negative PRs, never modify frozen main. If rights/branch protection or reviewer access absent, mark `BLOCKED`, not `PASS`.

### IV-11 — Apress publisher usability trial

Provide a rights-cleared proposal synopsis, frozen TOC, Ch16 manuscript, D-10/D-18 print proofs and labelled Meridian excerpt with no author briefing. Three reviewers separately answer: intended buyer, immediate problem solved, what book teaches differently than generic agent tutorial, one walkthrough takeaway, technical credibility, evidence limits, willingness to advance proposal, and three objections. Success is accurate explanation and actionable editorial feedback, **not** guaranteed acquisition. Include a comprehension exercise on why Gateway denial did not mean behavioural release success. Avoid conflating this with publisher commitment.

### IV-12 — lifecycle/retirement trial

Publish a disposable test knowledge item with a known dependent link; announce a safe hypothetical deprecation (e.g., a vendor API changed), verify dependency detection, replacement/no replacement, redirect or tombstone, search exclusion and preserved audit trail. Public frozen book and Meridian sources must remain untouched. Fail if retired content remains surfaced as current recommended guidance or dependent references silently break.

## Part 4 — Clean-room onboarding methodology

**Preconditions:** owner declares exact repository ref and SHA, a clean checkout script/README, current operating contract, valid handover and pinned fixture. No participant AI chat history, no private author notes, no earlier answers, no out-of-band coaching. Only normal GitHub repository search allowed. Record start/end timestamps and interruptions separately.

**Protocol:** (0) Read consent and tool restrictions; (1) provide three inputs: approved repo, operating system, handover packet; (2) ask participant to locate frozen D-10, D-14, D-18 and original request; (3) identify evidence version and reproduce fixture validation; (4) explain one conflict and one denial; (5) prepare a safe draft PR note or written next action; (6) independently complete exit questions. The test administrator says only “Use the provided sources” unless a documented access-blocking problem occurs.

**Measures:** total active minutes (excluding outage), time-to-first-correct-source, wrong-source selections, unprompted accuracy /10, number of incorrect actions, policy-violating attempts, source citations, requests for clarification, unsupported assumptions, reproducibility on fresh environment, and participant self-rated confidence. Capture participant's exact first answer before reviewer discussion. A tool/environment failure is not charged as learner misunderstanding; log both.

**Threshold:** eligibility is prerequisite. For a cohort of at least 3 independent onboarders: median ≤90 minutes and no individual >120 minutes absent documented external outage; each ≥8/10 accuracy; zero fabricated approvals/frozen edits; ≥90% assigned tasks complete without substantive coaching. If fewer than 3, report **pilot only**, not independent validation. Thresholds are programme hypotheses and may be revised through a separately versioned test protocol **before** evaluating results, never retroactively.

## Part 5 — Method reproducibility and inter-rater agreement

**Pre-register** test inputs, keys, rubric, case order/randomisation and outcome thresholds; do not move cutoffs after seeing results. Use at least two independent architects plus a security adjudicator for disputed authority answers. For each decision case rate on six dimensions: verdict, primary reason, secondary conditions, evidence mapping, scope/limitations and operational next step. Use both absolute correctness versus frozen evidence and agreement between participants.

**Agreement metric:** exact categorical verdict agreement = matching verdicts / shared cases (one-case agreement is inconclusive); per-dimension score difference, mean absolute difference; optionally Cohen's kappa after ≥10 genuinely distinct independently rated items across multiple cases. Because D-10, D-14, D-18 are only three distinct cases and may have fixed expected outcomes, **do not claim a statistically meaningful kappa** from three outcomes. Add ethically synthetic adversarial variants separately marked `DERIVED_TEST_CASE` and never merge into Meridian v1.0; variants cannot be cited as canonical fixture facts.

**Pass criterion:** for three primary canonical decisions, both architects must independently select the correct action status in all three; each ≥8/10 on every case; key reasons and evidence IDs correctly matched; no hard-stop errors. One mismatch in an actual authorisation verdict = NO GO for methodology claim. A failure discovered and correctly escalated is a valid outcome; a falsely confident permit is not.

## Part 6 — Knowledge usability, task learning and accessibility

A knowledge system is usable only when a person can **find the right item, recognise its authority, perform the task, detect an exception and explain why**. Test under permitted repository-only tools, not through a private guided conversation. Sample approved article, pattern, applied decision, cheat sheet and learning asset, with links pinned to release SHA. If any category has no approved item, mark `NOT_AVAILABLE`, not 0/10 fabricated success.

**Rubric (10 points):** find canonical item unaided (2); distinguish working/approved/deprecated (2); correctly apply decision/pattern (3); cite/test reproducibility (2); identify limitations/escalation (1). Separate time, number of clicks/searches, stale link count, ambiguity/confusion and accessibility failures. Learners progress by performance: read → classify → apply → analyse a failed case → challenge a claim. Do not infer a full junior-to-distinguished learning pathway from one tutorial. Require task-level outcome and pre/post demonstration before claiming teachability.

## Part 7 — Publication trial

**Inputs:** approved rights-cleared Apress proposal, TOC, Chapter 16, D-10/D-18 proof, labelled Meridian excerpt, independent reference checks, target buyer description. Optional Chapter 13 only after approved manuscript exists. **Reviewers:** developmental editor, independent technical architect, publisher/acquisitions-type reader (real publisher affiliation only when verified).

**Publisher test (rubric /10):** clear market/buyer (2); sample demonstrates instruction instead of outline (2); coherent differentiator without claims of primitive invention (2); technically credible/traceable evidence (2); realistic book scope/production feasibility (2). Also record 3 major objections, 3 unique useful elements, and a yes/no “would I request more?”; interest ≠ contract. Threshold each reviewer ≥7, none <6, no high-risk technical or rights defects. If not possible to recruit independent publisher-facing reviewer, status is `EDITORIAL_INTERNAL_ONLY`.

## Part 8 — Scoring, safety, GO / CONDITIONAL GO / NO GO

**Scoring:** each scenario 0–10 with prepublished anchored keys. Scores are independent from evidence-grade labels. No averaging can override a hard stop. Track both per-participant scores and median; no cherry-picking. Release scorecard includes: test ID; eligibility; build SHA; reviewer independence; attempted/finished; time; grade; hard stops; issue IDs; supporting evidence; disposition; retest.

| Outcome | Gate |
|---|---|
| **GO — limited methodology/knowledge MVP claim** | Required IV-01/02/03/04/07/09/10/11 completed with cohort and sources; all authorisation cases correct; all security/rights hard stops clear; each applicable test ≥8/10 except publication ≥7/10; two independent architects reach valid primary decisions; clean room onboarding median ≤90m; enforceable negative PR controls verified. IV-05/08/12 assessed when corresponding assets exist; missing required published deliverables block *claims about those products*, not the entire limited review. |
| **CONDITIONAL GO — internal supervised pilot only** | Sources and safety intact, no false permits, no rights leak; one or more non-safety comprehension/navigation scores 6–7/10, or time overruns, documented remediation+owner+retest date; no external “independently validated” or production claim. A missing required test is `NOT_RUN/BLOCKED`, not a conditional pass. |
| **NO GO — claimed programme efficacy** | Any false permit, production-safety overclaim, fabricated source, frozen data change, rights leak, bypass gate not functioning, wrong principal/tenant, security-dependent approval missing, unrepeatable baseline, or inability to run a required test. Stop corresponding claim/publication; preserve evidence and correct before rerun. |

**Decision dimensions are separate:** methodology GO is not security production GO; knowledge usability GO is not publisher readiness GO; publication quality GO is not regulatory approval. Publish a matrix of gated claims, not one universal green badge. If independence or minimum cohort missing, status `INSUFFICIENT_EVIDENCE` even with all scores 10/10. The limited GO gate is not a full ten-year operating-model endorsement.

## Part 10 — Running and reporting the programme

### A. Preparation checklist (coordinator, not an alternative governance process)

1. Reconcile PR #1 (frozen source import), PR #2 (knowledge/operating proposal), PR #3 (research); do not mistake an open PR for an approved main release. Record exact main SHA and branch protection.
2. Confirm documentary source authority and rights. Build a version-pinned **validation release bundle** from approved repository content; compare the original six Meridian artefacts, event ledger, D-10/14/18 and chapter 16 to frozen hashes. Never update fixture to make a test pass.
3. Obtain a qualified non-author technical reviewer and participant consent; log reviewer conflicts. Pre-register protocol SHA, scenario keys, outcome thresholds, and expected elapsed time; store keys away from participant distribution.
4. Make a clean clone or read-only distribution with a single start instruction and available tools; make no secret keys or real payment calls available.
5. Issue randomised IDs, schedule 20–90-minute sessions, record access failures and any coaching. Same inputs for architects A/B, differing user-visible role notes only when protocol requires it.
6. Run IV-01 through IV-12 only where prerequisites hold. Store raw answers unchanged and separate assessor interpretation; do not score `BLOCKED` as zero or pass.
7. Reconcile discrepancies, log corrective work against existing EX IDs or GitHub issue; record explicit `GO/CONDITIONAL GO/NO GO/INSUFFICIENT_EVIDENCE` for each claim.
8. Publish a redacted evaluation summary, including failed cases, missing participants, limits, reviewer identity role, and study protocol hash. Gate rights/confidentiality before public release.

### B. Evidence packet required for each run

`RUN-ID` unique, `IV-ID`, protocol version/hash, source baseline SHA, fixture ID/hash, participant pseudonym and declared independence, environment/tool versions, start/end active seconds, allowed access, unaltered submitted response, criterion scores, errors/assistance, evidence paths/hashes, reviewer role and verdict, challenge/remediation link, retest linkage, retention and confidentiality designation.

Use `validation-run-template.json` supplied with this package. Use `SCENARIO-CATALOGUE.csv` and `SCORING-RUBRIC.csv` to prepare participant-specific task cards; **never supply the answer key in the participant packet**. Participant distribution also excludes this master coordinator protocol; use task cards and approved canonical source files only. Store full original responses and keys separately from public summary.

### C. Evaluation integrity and repeatability

Each case has an expected adverse test; the reviewer should actively seek conditions under which the claimed method fails. After a defect is discovered, use an independently regraded retest; do not retroactively overwrite original submissions or scores. Distinguish *participant mistake*, *faulty documentation*, *environment failure*, and *control defect*. The coordinator is responsible for audit trail, not for altering expected answers post hoc.

**Exit deliverable:** an independent signed review summary with a per-claim evidence ledger, failed and passed tests, scope/rights limitations, actionable defects and release disposition. Until that exists, status remains `SPECIFIED / NOT INDEPENDENTLY VALIDATED`.
