# The Enterprise AI Agent Fabric — Signature IP and Thought-Leadership Platform
**Editorial source:** Frozen 58-chapter development blueprint, 30-decision Atlas, Style Bible v1.2 and the prior commercial acquisition analysis. **Plan issued:** 9 November 2026. **Programme:** December 2026–November 2027. **Status:** publishing/marketing specification; no audience growth, conference acceptance or deployed system is claimed.

**Non-negotiable boundary:** This plan does not change any Structural Layer, Control Plane, chapter, decision ID, default, playbook or Meridian event. Brand labels below describe *ways to teach* the existing material, not additional architectural components. The Style Bible remains authoritative for reproduced manuscript excerpts and diagrams.

## Executive answer
The strongest asset is the **30-page Decision Atlas**, linked to a second asset: an auditable sequence from a requested action to delegated authority, Gateway enforcement, verification and an inspectable evidence record. The **4×8 architecture** makes the method navigable. Autonomy and context contracts make it teachable. None of those component words is inherently exclusive or wholly original. The marketable contribution is the completed and demonstrable *system of decisions and artefacts*.

**Do not sell these as invented industry standards.** The term Agent Fabric is in commercial use by Salesforce/MuleSoft; `Autonomy Envelope`, `Actor Chain`, `Context Manifest`, `Evidence Envelope` and `Earned Autonomy` have documented public uses. The named author collection can still become recognisable through strong examples, diagrams, training and third-party uptake. Details and sources appear in the final provenance section.

## Part 3 — Ten conference-ready talks
All abstracts use Meridian as a clearly fictional scenario, include a practical output and avoid unverifiable implementation claims. Recommended lengths are 30–45 minutes plus questions; proposals must be adapted to a specific event’s CFP instructions and current deadlines.
### T01 — Should You Build a Shared AI Agent Platform at All?
**Audience:** Enterprise architecture leaders; CIO/CTO practitioners. **Related chapters:** 1, 4–6, 23, 41. **Related decisions:** D-01, D-02, D-03.

**Abstract.** The fifth agent use case often triggers a proposal for a shared platform. But a shared Fabric creates support, security and coordination obligations before it produces reuse. This session follows Meridian Financial as its sponsor rejects a fifth stand-alone pilot and asks for an evidence-based alternative appraisal. We compare demand, overlapping controls, tenant requirements and ongoing cost without assuming that platformisation wins. Attendees use an example one-page decision to separate a no-build case from a justified shared service. The goal is not to prescribe one topology. It is to show the evidence needed to choose.

**Three takeaways:** Define the shared-controls demand threshold; Build a no-Fabric alternative; Record a reversible sourcing decision.

### T02 — Who Authorised This Agent? Delegation That Cannot Expand
**Audience:** Security architects; IAM leads; enterprise architects. **Related chapters:** 9, 15–16, 19, 40. **Related decisions:** D-05, D-10, D-19, D-20.

**Abstract.** An agent acting for a person is not the same as a person making a request. Delegated execution introduces identity chains, purpose restrictions, expiring approvals and new failure points. Using a fictional payment-dispute task, this session tracks the original human request through two agent hops and a tool call. The example shows what the Identity Control Plane issues, what the Gateway verifies, what a delegated step cannot change, and which evidence survives an incident. It also demonstrates an attempted privilege expansion that must fail. The technical concepts draw on established delegation patterns; the value is the enterprise decision and evidence sequence.

**Three takeaways:** Separate identity issuance from action enforcement; Demonstrate scope attenuation; Record the rejected delegation evidence.

### T03 — A Gateway Diagram Is Not a Security Control: Prove Non-Bypassability
**Audience:** Platform security; cloud platform engineering; security operations. **Related chapters:** 12, 16, 27, 48. **Related decisions:** D-09, D-10, D-18, D-28.

**Abstract.** Architectures routinely place a gateway between an agent and its tools. That diagram says little about what happens when an adapter holds credentials or can reach an endpoint directly. This session develops a concrete deny-path exercise for a mutable external action. It identifies necessary controls across credential issuance, egress rules, adapter identity, policy availability and receipt correlation. The Meridian scenario includes a denied refund-like permission expansion and demonstrates the difference between policy documentation and enforcement evidence. Participants leave with a negative-test outline that can be adapted to their own Fabric.

**Three takeaways:** Identify bypass paths; Define negative tests; Capture enforceable denial receipts.

### T04 — The Context Manifest: What Did the Agent Actually Know?
**Audience:** Data architects; knowledge engineers; AI governance. **Related chapters:** 13, 18, 21, 57. **Related decisions:** D-11, D-12, D-14, D-24.

**Abstract.** When two enterprise systems disagree, retrieving both records does not resolve which is correct. This talk uses a synthetic retail case with conflicting product status to show the Context Structural Layer as more than a prompt assembly service. A context manifest identifies the retrieved sources, versions, access classes and reconciliation result for a single run. The talk traces a conflict that is deliberately escalated rather than guessed, followed by a durable-memory write that requires provenance and retention rules. The aim is to make semantic accountability auditable without claiming that context manifests are a new invention.

**Three takeaways:** Distinguish retrieval from source authority; Specify a context manifest; Escalate unresolved semantic conflict.

### T05 — Earned Autonomy Is a Release Decision, Not a Model Property
**Audience:** AI governance; risk leaders; platform leads. **Related chapters:** 2, 9, 18, 33, 47. **Related decisions:** D-05, D-16, D-22, D-23.

**Abstract.** A model that performs well in a benchmark has not thereby earned permission to change business records. This session separates behavioural verification from business risk acceptance and delegated authority. Using Meridian’s pilot release, the first gate fails on conflicting documents. A narrowed, read-only task later passes. We examine the evidence packet, the owner who approves each autonomy boundary, and the operational conditions that require suspension or retraining. Participants leave with an example autonomy envelope and a release-gate worksheet, not an unsupported maturity score.

**Three takeaways:** Explain who sets permission; Specify assertion-backed promotion; Define downgrade and rollback triggers.

### T06 — SRE for Agent Workloads: Queues, Retries and Resumption
**Audience:** SRE; platform operations; reliability engineering. **Related chapters:** 11, 14, 17, 36. **Related decisions:** D-07, D-08, D-15, D-24, D-27.

**Abstract.** CPU graphs alone do not explain an agent queue that is growing while retry costs rise. Long-lived trajectories create failure modes involving uncertain tool outcomes, interrupted checkpoints and expired delegation. In this case-led session, Meridian’s SRE team diagnoses queue-age saturation and then exercises a recovery path that requires fresh authority before a resumed tool action. The discussion covers the difference between step success and business-task completion, as well as which service-level indicators should trigger operational action. The audience receives a bounded-workload runbook skeleton and a recovery test checklist.

**Three takeaways:** Find queue-based load signals; Handle unknown tool outcomes; Reauthorise after resume.

### T07 — Stop Optimising Tokens: The Cost per Successful Task
**Audience:** FinOps practitioners; AI platform leads; engineering managers. **Related chapters:** 8, 20, 38, 41. **Related decisions:** D-17, D-26.

**Abstract.** Choosing a cheaper model can increase total operating cost if the workflow retries, escalates to people or fails more often. This session develops a transparent, synthetic accounting example that charges model calls, tool usage, human review, platform support and failed attempts to a defined task outcome. It then connects cost attribution to routing and budget decisions without pretending that a single cost metric captures business value. The practical exercise is a cost-per-success ledger with clearly labelled assumptions and sensitivity tests. Participants can adapt the method to their own measures and funding decisions.

**Three takeaways:** Define the accepted-success denominator; Attribute total cost including failed attempts; Choose budget/routing conditions.

### T08 — From One Agent to Twelve Use Cases: Who Owns the Platform?
**Audience:** Platform engineering leaders; enterprise architects; domain product owners. **Related chapters:** 3, 6, 30–32, 35, 44–46. **Related decisions:** D-03, D-04, D-06, D-29.

**Abstract.** Enterprise agent adoption changes organisation design as much as runtime architecture. Meridian Financial begins with isolated pilots, then encounters conflicting onboarding requests from five domain teams. This session follows the fictional progression to twelve live use cases, showing which decisions belong to the Fabric team, domain owners, security and FinOps. It separates catalogue standardisation from arbitrary central control and discusses when a use case should remain outside a shared Fabric. The main output is a decision-rights map and a sample onboarding contract. The scenario is explicitly synthetic, not evidence of a deployed twelve-agent portfolio.

**Three takeaways:** Identify platform versus domain ownership; Apply onboarding exceptions; Avoid false scaling claims.

### T09 — The First Agent Incident: Denial, Quarantine and Evidence
**Audience:** Security operations; platform SRE; enterprise risk. **Related chapters:** 13, 16–18, 21, 37, 40, 48. **Related decisions:** D-12, D-18, D-24, D-28.

**Abstract.** A poisoned knowledge record instructs an agent to make an unauthorised external call. The Gateway refuses the action, but the incident is not over: the source may have entered durable memory, delegated work may still be queued, and assurance teams need evidence. This fictional case walks through incident command, containment authority, quarantine, evidence preservation and safe resumption. It shows why an API denial cannot be treated as a complete security verdict. Attendees leave with a minimal incident packet and a set of decision points for suspending or restoring a use case.

**Three takeaways:** Contain ongoing work; Preserve linked evidence; Specify safe restoration gates.

### T10 — Can You Retire Your AI Agent Platform? Prove the Exit
**Audience:** Enterprise architects; technology risk; platform owners. **Related chapters:** 21, 34, 40, 49–50, 57. **Related decisions:** D-25, D-29, D-30.

**Abstract.** Most adoption programmes talk about onboarding agents; few lead with how to leave. Retirement requires more than turning off a runtime. Permissions must be revoked, durable memory addressed under retention rules, audit material preserved, dependent use cases migrated and residual costs closed. Meridian retires a legacy pilot, then runs a rehearsal for replacing the still-live Fabric. This session presents a fictional retirement certificate and an exit-readiness decision tree. It explains how to distinguish actual deletion evidence from a promise that data has been deleted.

**Three takeaways:** Define retirement completeness; Test vendor portability; Produce an inspectable exit record.

### 1. The 30-Decision Enterprise AI Atlas
